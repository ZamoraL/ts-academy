Cuando dos componentes necesitan **el mismo** estado, se mueve al **ancestro común más cercano** y se baja por props. Esto se llama *levantar el estado* (lifting state up).

## El ejemplo del acordeón

Dos paneles; solo uno puede estar abierto a la vez.

Si cada panel tiene su propio `abierto`, no pueden coordinarse. Así que el estado sube al padre:

```jsx
function Acordeon() {
  const [activo, setActivo] = useState(0)
  return (
    <>
      <Panel titulo="Acerca de" abierto={activo === 0} onMostrar={() => setActivo(0)}>
        Texto del primer panel
      </Panel>
      <Panel titulo="Contacto" abierto={activo === 1} onMostrar={() => setActivo(1)}>
        Texto del segundo panel
      </Panel>
    </>
  )
}

function Panel({ titulo, abierto, onMostrar, children }) {
  return (
    <section>
      <h3>{titulo}</h3>
      {abierto ? <p>{children}</p> : <button onClick={onMostrar}>Mostrar</button>}
    </section>
  )
}
```

- **Los datos bajan** por props (`abierto`).
- **Los eventos suben** por callbacks (`onMostrar`).

## Componentes controlados y no controlados

- `Panel` es **controlado**: su comportamiento lo decide el padre mediante props.
- Un panel con su propio `useState` sería **no controlado**: más fácil de usar, menos flexible.

Es la misma idea que los inputs controlados de la unidad anterior.

## Única fuente de verdad

Para cada dato, decide **qué componente es su dueño**. Ese componente tiene el estado; los demás lo reciben. Evita duplicar el mismo dato en dos estados.

## Patrón típico: lista + formulario + resumen

```jsx
function App() {
  const [tareas, setTareas] = useState([])
  return (
    <>
      <Formulario onAgregar={(t) => setTareas([...tareas, t])} />
      <Lista tareas={tareas} onBorrar={(id) => setTareas(tareas.filter((t) => t.id !== id))} />
      <Resumen total={tareas.length} />
    </>
  )
}
```

`Formulario`, `Lista` y `Resumen` no se conocen entre sí: todo pasa por `App`. Cada uno es simple y fácil de probar.
