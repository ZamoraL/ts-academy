Tu lista de tareas del bloque A, ahora con interfaz. Vas a construir una app completa en un archivo, con varios componentes.

## Requisitos

Un componente `App` (exportado por defecto) que muestre:

1. **Formulario** con un input con label `Nueva tarea` y un botón `Agregar`. Al enviar (también con Enter):
   - si el título (sin espacios alrededor) está vacío, no hace nada;
   - si no, añade la tarea y limpia el input.
2. **Filtros**: tres botones `Todas`, `Pendientes` y `Hechas`. El activo tiene `aria-pressed="true"`.
3. **Lista** (`<ul>`): cada tarea es un `<li>` con:
   - un checkbox con label igual al título de la tarea, que marca/desmarca como hecha;
   - un botón `Borrar` con `aria-label="Borrar <título>"`.
4. **Resumen**: un párrafo `N pendientes` (o `1 pendiente` en singular).
5. Si la lista (filtrada) está vacía: el texto `No hay tareas`.

## Estructura sugerida

```
App          ← estado: tareas, filtro
├─ Formulario  (onAgregar)
├─ Filtros     (filtro, onCambiar)
├─ Lista       (tareas, onAlternar, onBorrar)
│   └─ ItemTarea
└─ Resumen     (pendientes)
```

## Lo que practicas

Todo el bloque: componentes, props, children, renderizado condicional, listas con `key`, eventos, estado con arrays sin mutar, formularios controlados y levantar el estado.

## Accesibilidad

`aria-pressed` y `aria-label` no son decoración: describen la interfaz para lectores de pantalla, y los tests los usan para encontrar elementos igual que lo haría una persona. Testing Library promueve exactamente esto: *probar la interfaz como la usa el usuario*.
