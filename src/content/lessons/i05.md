Los gastos guardados viven en un servidor. Vas a cargarlos con `fetch` y **validarlos con Zod** antes de que entren a tu app.

## La API

```
GET https://api.test/gastos → [{ id, descripcion, monto, categoria, fecha }, ...]
```

## El schema refleja el tipo

```ts
const GastoSchema = z.object({
  id: z.string(),
  descripcion: z.string(),
  monto: z.number(),
  categoria: z.enum(CATEGORIAS),
  fecha: z.string().regex(/^\d{4}-\d{2}-\d{2}$/),
})
```

`z.enum(CATEGORIAS)` acepta directamente tu tupla `as const`. Y puedes comprobar que el schema y tu interfaz no se desincronicen:

```ts
type DesdeSchema = z.infer<typeof GastoSchema>
// si Gasto y DesdeSchema difieren, un test de tipos lo detecta
```

En muchos proyectos se invierte: el schema es la fuente de verdad y `type Gasto = z.infer<typeof GastoSchema>`.

## Capa de API

```ts
export async function obtenerGastos(): Promise<Gasto[]> {
  const r = await fetch('https://api.test/gastos')
  if (!r.ok) throw new Error(`HTTP ${r.status}`)
  return z.array(GastoSchema).parse(await r.json())
}
```

Si el servidor manda un monto como string o una categoría desconocida, `parse` lanza un error **aquí**, no tres componentes más allá.

## El hook

Reutiliza el patrón de `useFetch` (unidad H10), pero recibiendo una **función** que obtiene los datos:

```ts
function usePeticion<T>(obtener: () => Promise<T>): EstadoPeticion<T>
```

Así el hook no sabe nada de URLs ni de Zod: solo de estados de carga. Ojo con las dependencias del efecto: si `obtener` es una función nueva en cada render, el efecto se repetiría sin fin. Pásale una función estable (declarada fuera del componente).

## Errores de validación vs de red

Ambos llegan al `catch`. Puedes distinguirlos:

```ts
catch (e) {
  const mensaje = e instanceof z.ZodError ? 'El servidor envió datos inválidos' : 'No se pudo conectar'
}
```
