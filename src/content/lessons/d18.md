Vas a modelar el ciclo de vida de un **pedido** con una *máquina de estados* tipada. Es un patrón muy usado en apps reales (y con `useReducer` en React).

## Estados

Define `type Pedido` como una discriminated union por la propiedad `estado`:

| `estado` | Datos |
|---|---|
| `'carrito'` | `items: string[]` |
| `'pagado'` | `items`, `pagoId: string` |
| `'enviado'` | `items`, `pagoId`, `tracking: string` |
| `'entregado'` | `items`, `pagoId`, `tracking`, `fecha: string` |
| `'cancelado'` | `motivo: string` |

## Eventos

Define `type Evento` como otra unión, por la propiedad `tipo`:

- `{ tipo: 'agregar'; item: string }`
- `{ tipo: 'pagar'; pagoId: string }`
- `{ tipo: 'enviar'; tracking: string }`
- `{ tipo: 'entregar'; fecha: string }`
- `{ tipo: 'cancelar'; motivo: string }`

## Transiciones

Implementa `transicion(pedido: Pedido, evento: Evento): Pedido`:

- `agregar`: solo en `carrito`; añade el item.
- `pagar`: solo desde `carrito` y si hay al menos un item.
- `enviar`: solo desde `pagado`.
- `entregar`: solo desde `enviado`.
- `cancelar`: desde `carrito` o `pagado`.

Cualquier transición no permitida lanza `Error('Transición inválida: <estado> → <tipo>')`, por ejemplo `'Transición inválida: enviado → cancelar'`. Si el carrito está vacío al pagar, el mismo error vale.

Implementa también `resumen(pedido: Pedido): string` con un `switch` **exhaustivo** (usa `never` en el `default`):

- carrito: `'Carrito con N items'`
- pagado: `'Pagado (pagoId)'`
- enviado: `'Enviado (tracking)'`
- entregado: `'Entregado el fecha'`
- cancelado: `'Cancelado: motivo'`

## Pistas

- Escribe `assertNever` primero.
- En `transicion`, un `switch (evento.tipo)` y dentro comprueba `pedido.estado`. TS estrechará ambos.
- Los tests de tipos comprueban, por ejemplo, que un pedido `'pagado'` sin `pagoId` sea un error.
