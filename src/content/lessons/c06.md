## any: apagar el chequeo

`any` significa "no compruebes nada sobre este valor". Todo está permitido:

```ts
let obj: any = { x: 0 }
obj.foo()          // sin error
obj = 'hola'       // sin error
const n: number = obj // sin error
```

Es una puerta de escape útil para migrar código JS, pero **cada `any` es un agujero** por donde se cuelan los bugs que TS existe para evitar. Evítalo.

## noImplicitAny

Cuando TS no puede deducir un tipo y no lo anotas, usa `any` **implícitamente**. Con `noImplicitAny` (incluido en `strict`) eso es un error:

```ts
function saludar(nombre) {
// Error: Parameter 'nombre' implicitly has an 'any' type.
  return 'Hola ' + nombre
}
```

Esto te obliga a anotar los parámetros. Es bueno.

## unknown: la alternativa segura

`unknown` también acepta **cualquier valor**, pero no te deja **usarlo** hasta que compruebes qué es:

```ts
function procesar(valor: unknown) {
  valor.toUpperCase()
  // Error: 'valor' is of type 'unknown'.

  if (typeof valor === 'string') {
    valor.toUpperCase() // ✓ aquí TS sabe que es string
  }
}
```

| | `any` | `unknown` |
|---|---|---|
| Acepta cualquier valor | ✓ | ✓ |
| Puedes usarlo sin comprobar | ✓ (peligroso) | ✗ |
| Se puede asignar a otros tipos | ✓ | ✗ (solo tras comprobar) |

**Regla:** cuando no sabes qué llega (JSON, datos de usuario, un `catch`), usa `unknown` y compruébalo.

## Dónde aparece any sin que lo pidas

- `JSON.parse(...)` devuelve `any`.
- `const lista = []` sin anotar.
- Librerías sin tipos.

Anótalos o conviértelos a `unknown`:

```ts
const datos: unknown = JSON.parse(texto)
```

## catch

Con `strict`, el error de un `catch` es `unknown`, porque en JS se puede lanzar cualquier cosa:

```ts
try {
  // ...
} catch (e) {
  if (e instanceof Error) console.log(e.message)
}
```
