Cuando el estado tiene muchas formas de cambiar, `useReducer` concentra toda la lógica de actualización en una función pura: el **reducer**.

```tsx
import { useReducer } from 'react'

interface Estado {
  contador: number
  paso: number
}

type Accion =
  | { tipo: 'incrementar' }
  | { tipo: 'decrementar' }
  | { tipo: 'reiniciar' }
  | { tipo: 'cambiarPaso'; paso: number }

function reducer(estado: Estado, accion: Accion): Estado {
  switch (accion.tipo) {
    case 'incrementar':
      return { ...estado, contador: estado.contador + estado.paso }
    case 'decrementar':
      return { ...estado, contador: estado.contador - estado.paso }
    case 'reiniciar':
      return { ...estado, contador: 0 }
    case 'cambiarPaso':
      return { ...estado, paso: accion.paso } // TS sabe que accion tiene paso
  }
}

function Contador() {
  const [estado, dispatch] = useReducer(reducer, { contador: 0, paso: 1 })
  return (
    <>
      <p>{estado.contador}</p>
      <button onClick={() => dispatch({ tipo: 'incrementar' })}>+</button>
      <button onClick={() => dispatch({ tipo: 'cambiarPaso', paso: 5 })}>Paso 5</button>
    </>
  )
}
```

## Por qué TS y reducers encajan tan bien

Las acciones son una **discriminated union**:

```tsx
dispatch({ tipo: 'incrementr' })
// Error: Type '"incrementr"' is not assignable to type '"incrementar" | ...'

dispatch({ tipo: 'cambiarPaso' })
// Error: Property 'paso' is missing...
```

Y con un `default` exhaustivo, si añades una acción nueva y olvidas manejarla, TS te avisa:

```tsx
default: {
  const _exhaustivo: never = accion
  return estado
}
```

## Reglas del reducer

- **Puro**: mismo estado + misma acción = mismo resultado. Sin `fetch`, sin `Date.now()`, sin `Math.random()` (pásalos dentro de la acción si los necesitas).
- **No muta**: devuelve un estado nuevo.

Al ser una función pura sin React, el reducer se puede **probar** aisladamente, como cualquier función:

```ts
expect(reducer({ contador: 0, paso: 2 }, { tipo: 'incrementar' })).toEqual({ contador: 2, paso: 2 })
```

## ¿useState o useReducer?

- Pocas actualizaciones simples: `useState`.
- Muchas acciones que tocan el mismo estado, o la siguiente actualización depende de la anterior de forma compleja: `useReducer`.
- La lógica se vuelve difícil de seguir repartida en varios handlers: `useReducer`.
