Llevas todo el curso **pasando** tests. Ahora entiende cómo se escriben, porque en un proyecto real los escribirás tú.

## Las herramientas

En tu proyecto Vite:

```bash
npm install -D vitest @testing-library/react @testing-library/user-event @testing-library/jest-dom jsdom
```

- **Vitest**: ejecuta los tests (`npm test`). Misma API que Jest.
- **Testing Library**: renderiza componentes y los consulta como un usuario.
- **jsdom**: un DOM simulado para Node.

Esta misma app tiene tests con Vitest: mira `src/lib/scheduler.test.ts`.

## Anatomía de un test

```tsx
import { render, screen } from '@testing-library/react'
import userEvent from '@testing-library/user-event'
import { describe, it, expect } from 'vitest'

describe('Contador', () => {
  it('suma al hacer clic', async () => {
    render(<Contador />)                                           // 1. preparar
    await userEvent.click(screen.getByRole('button', { name: '+' })) // 2. actuar
    expect(screen.getByText('1')).toBeInTheDocument()              // 3. comprobar
  })
})
```

## Consultas: prioridad recomendada

| Consulta | Cuándo |
|---|---|
| `getByRole('button', { name: 'Guardar' })` | Casi siempre: refleja la accesibilidad |
| `getByLabelText('Email')` | Campos de formulario |
| `getByText('Hola')` | Texto no interactivo |
| `getByTestId('x')` | Último recurso |

Variantes: `getBy` (lanza si no existe), `queryBy` (devuelve `null`: para comprobar que algo **no** está), `findBy` (async: espera a que aparezca).

## Qué probar

- **Comportamiento visible**, no detalles de implementación. "Al enviar el formulario aparece el gasto en la lista", no "el estado `gastos` tiene longitud 1".
- Funciones puras (reducer, utilidades): con tests unitarios directos, sin render.
- Casos límite: lista vacía, errores de red, datos inválidos.

## TDD: tests primero

En este ejercicio los tests ya están escritos (los ves en el enunciado) y tú escribes el componente que los hace pasar. Es *Test-Driven Development*: el test define el comportamiento esperado antes de que exista el código. Es una forma excelente de trabajar con requisitos claros.
