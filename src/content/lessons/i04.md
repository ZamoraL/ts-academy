La app necesita agregar, borrar, editar y cargar gastos. Con varios `useState` la lógica quedaría repartida; un **reducer** la concentra en una función pura y probada.

## Las acciones

```ts
export type Accion =
  | { tipo: 'agregar'; gasto: Gasto }
  | { tipo: 'borrar'; id: string }
  | { tipo: 'editar'; id: string; cambios: CambiosGasto }
  | { tipo: 'cargar'; gastos: Gasto[] }
```

Fíjate en `agregar`: recibe el gasto **ya con id**. ¿Por qué no generar el id dentro del reducer?

```ts
case 'agregar':
  return [...estado, { ...accion.datos, id: crypto.randomUUID() }] // ❌ impuro
```

Un reducer debe ser **puro**: mismo estado + misma acción = mismo resultado. `crypto.randomUUID()` o `Date.now()` rompen eso (y hacen los tests impredecibles). Genera el id **antes** de despachar:

```ts
dispatch({ tipo: 'agregar', gasto: { ...nuevo, id: crypto.randomUUID() } })
```

## Editar con Partial

```ts
case 'editar':
  return estado.map((g) => (g.id === accion.id ? { ...g, ...accion.cambios } : g))
```

`CambiosGasto = Partial<NuevoGasto>` no incluye `id`, así que una edición nunca puede cambiar el id. Los tipos protegen las reglas del dominio.

## Exhaustividad

Con el `default` con `never`, si en el futuro añades `{ tipo: 'duplicar'; id: string }` y olvidas el caso, TS te lo marca.

## Probar el reducer

Al ser una función pura, los tests son simples y no necesitan interfaz:

```ts
const s1 = reducer([], { tipo: 'agregar', gasto: g1 })
expect(s1).toEqual([g1])
```

## Conectarlo

```tsx
const [gastos, dispatch] = useReducer(reducer, [])
```

TS infiere el tipo del estado a partir del reducer. Y `dispatch` solo acepta objetos `Accion` válidos.
