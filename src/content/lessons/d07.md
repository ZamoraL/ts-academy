## never: el tipo vacío

`never` es el tipo **sin valores**. Aparece cuando TS ha descartado todas las posibilidades:

```ts
function f(x: string | number) {
  if (typeof x === 'string') return
  if (typeof x === 'number') return
  x // never: aquí no puede llegar nada
}
```

También es el retorno de funciones que **nunca terminan normalmente**:

```ts
function fallar(mensaje: string): never {
  throw new Error(mensaje)
}
```

## Comprobación de exhaustividad

Un valor de cualquier tipo **no** se puede asignar a `never`. Esto da un truco poderoso: asegurarte de manejar **todos** los casos de una unión.

```ts
type Forma = Circulo | Cuadrado

function area(forma: Forma): number {
  switch (forma.kind) {
    case 'circulo':
      return Math.PI * forma.radio ** 2
    case 'cuadrado':
      return forma.lado ** 2
    default: {
      const _exhaustivo: never = forma
      return _exhaustivo
    }
  }
}
```

Hoy compila: en el `default`, `forma` es `never`. Pero si alguien añade un tipo:

```ts
type Forma = Circulo | Cuadrado | Triangulo
```

…aparece un error **justo en el switch que olvidó el caso**:

```
Type 'Triangulo' is not assignable to type 'never'.
```

En proyectos grandes, esto convierte "olvidé actualizar un switch" de bug en producción a error de compilación.

## Una función auxiliar

Para no repetir el patrón:

```ts
function assertNever(x: never): never {
  throw new Error('Caso no manejado: ' + JSON.stringify(x))
}

switch (estado.tipo) {
  case 'a': ...
  case 'b': ...
  default:
    return assertNever(estado)
}
```

Además del error de compilación, si de algún modo llega un valor inesperado en runtime (por ejemplo, de una API), lanza un error claro.

## Funciona con if también

```ts
function nombre(m: 'GET' | 'POST'): string {
  if (m === 'GET') return 'obtener'
  if (m === 'POST') return 'crear'
  return assertNever(m)
}
```
